# 问卷数据集（研究用）

`surveys.json` —— 用 `npm run harvest` 采集的真实问卷结构，**只进问卷页、不提交**。
用途是给「自动作答」的设计提供实测依据，而不是靠猜。

## 采集方式与副作用

到达问卷页必须 POST 一次确认页（实测确认：**POST 确认页不等于投递**，
真正的投递是问卷页上的送信按钮，采集器绝不点它）。因此：

- brandcollection 流程的确认页带 `addbrand`（默认勾选且为投递必需）→ 会**关注对应品牌**
- brandFanClub 流程没有该复选框 → 无此副作用
- 全程按 `PACING` 的人类速度节奏

采集后奖品仍是「未投递」状态，之后正常跑批次即可完成投递。
**已投递过的奖品采不到题目**（问卷已答），会记成 `questions: []`。

## 2026-08-20 首次采集的结论

13 个奖品，9 个采到题目（另 4 个已投递过），共 **45 道题**。
按选项集合归类后，**45 道题实际只有 3 种题型**：

| 题型 | 出现 | 选项 | 词库命中 |
| --- | --- | --- | --- |
| 品牌/商品使用经验（radio） | 18 次 | 5 | 1（「使ったことはないが、よく知っている」） |
| 认知渠道（checkbox） | 18 次 | 9 | 1（「SNS・動画SNS・ブログ」） |
| 观后意向（checkbox） | 9 次 | 9 | 2（サンプル・テスター / 購入してみたい） |

**覆盖率 45/45，零留空**；radio 组均为单命中（无歧义）；
兜底类选项（「その他」「今回初めて知った」等）均未被误选。

⚠️ 已确认的缺陷（与覆盖率无关）：

1. **全角/半角**：词库里是全角 `＠ｃｏｓｍｅ`，而真实选项是半角 `@cosme` → 不命中。
   这一项不影响作答（同题有 SNS 命中），但说明匹配前需要做字符正规化。
2. **题干没抓到**：本次采集的 `prompt` 只有字段名。因此依赖题干文本的
   `needsManualChoice()`（识别「ご希望の…お選びください」这类需人工决定的题）
   在 present-blog 问卷上**永远不会触发**——这是真实的功能缺口。
3. **两个模式的 radio 处理不一致**：`present-blog` 命中一个即 `break`，
   `is-enq` 不 break（等于「最后一个命中的选项胜出」）。本次数据里 radio 都是单命中，
   所以没暴露，但属于潜在不一致。
4. 样本偏窄：这 45 道题全部来自 present-blog 流程（is-enq 的 4 个奖品都已投递）。
   is-enq 的题型（含 `prof_*` 个人资料字段、多奖品选择题）没进本次数据集。

## 2026-08-20 修补（依据上述数据）

结论是**不必推翻词库模式，只需三处针对性修补**（判据集中到 `packages/core/src/answering.ts`，
两套流程共用 `apps/runner/src/cosme/patterns/survey-common.ts`）：

1. **字符正规化**（NFKC + 小写 + 去空白）。⚠️ 踩过的错：只折选项文本没用，
   **词库那边也要折**——库里存全角 `＠ｃｏｓｍｅ`、选项是半角 `@cosme`，
   不折成同一形式永远不命中。
2. **题干抓取修好了**。实测结构是 `div.qa > div.answer`，题干 = `.qa` 文本减去 `.answer` 文本；
   此前直接取父元素文本会把选项混进来、减完成空串，导致 `needsManualChoice()`
   **永远不触发**——「ご希望の…お選びください」这类该问用户的题会被词库自动答掉。
   同时把标记词从 `選びください` 放宽成 `選び`，覆盖 `お選び下さい` 的汉字写法。
3. **radio 统一取第一个命中**。原先两套流程不一致（一个命中即停、一个不停＝最后命中者胜出）。

另外补了**反转语义排除**（`NEGATION_MARKERS`）。这一条是正规化生效后**从真实数据里冒出来的**：
`「@cosme以外のWEBサイト・アプリ」` 只因含 `@cosme` 就被选中，而那条词的本意是选 @cosme 本身。
标记列表必须精确——不能图省事写「ない」，因为「使ったことはないが、よく知っている」正是要选的答案。

回归结果（45 题）：决策全部为 `select`，radio 单选、checkbox 合理多选，
`@cosme以外` 已被正确排除，两种「お選びください/下さい」写法均能识别为需人工。

## 奖品来源盘点（2026-08-20 系统侦察 `/present/` 导航页）

| 来源 | 路径 | 数量 | 状态 |
| --- | --- | --- | --- |
| ブランドコレクション | `/brandcollection/present/` | 3 | ✅ 已支持 |
| ブランドファンクラブ限定 | `/brandfanclub/present` | 10 | ✅ 已支持 |
| ⭐ **手机版全量列表** | **`s.cosme.net/present/`**（须手机 UA） | **45** | ✅ 已支持（`mobileAll`） |
| プロデュースメンバー限定 | `/present/detail/present_id/<n>` | 2 | ⚠️ 未支持（已含在 mobileAll 里？待核） |
| @cosme ポイント | `point.cosme.net/tsukau/present` | ? | ⚠️ 未支持（积分兑换类，可能不是抽奖） |

**结论：不要只看桌面版。** 站点自报 57 件，桌面三页合计只有 13 个；
剩下 45 个只在手机版全量列表里。实测三来源合计入库 58 个、全部有图。

⚠️ 两个容易误判的点：

- brandfanclub 页面写着「（55件）」且页面上确有 55 个 `.psnt-ttl`，**但只有 10 个是可投递奖品**。
  另外 45 个是「注目ブランド」「注目ランキング」区块的品牌推广卡片，链接指向
  `/brand/brand_id/<n>/top`（品牌主页）而非奖品入口。解析器只认
  `/beautist/article/` 是正确的，别被「55件」误导去抓那 45 个。
- プロデュースメンバー限定那批的路径是 `/present/detail/…` 而非
  `/brandcollection/present/detail/…`，且 ID 段完全不同（19614 vs 12057）。

## 2026-08-21 奖品数据核查（`npm run audit`）

起因：界面上「期间」列出现了 `計5名様現品 · うるおいケアしながら、自然な血色感を。`
——扫描时把「数量 + 文案」塞进了展示为期间的 `description` 字段，字段语义混乱。

**建模修正**：`description` 拆成三列，各有明确语义，并加了「只放日期区间」的约束注释：

| 字段 | 内容 | 来源 |
| --- | --- | --- |
| `period` | **只放日期区间**（`8/17～8/23`） | 列表页括号 或 详情页「応募受付：」 |
| `quantity` | 数量与形式（`計20名様現品`） | 列表页 `.psnt-num` 或详情页正文 |
| `tagline` | 一句话文案 | 列表页 `.psnt-copy` 或详情页标题 |

**核查工具** `npm run audit [--fix] [--limit N]`：逐个访问奖品详情页，以页面为真值
与库里逐项比对（期间/数量/图片/是否还开放应募），只读、绝不点投递按钮，按 PACING 节奏。
产物 `docs/research/audit.json`。

首次全量核查（48 个）结果：**41 个无问题**，7 个有真实原因、非 bug：

- 3 个「页面无应募入口」→ 都是**已投递**的（站点投递后入口消失，与「不标注已应募」并不矛盾：
  入口没了但页面仍显示「応募する」文案的情况也见过，故 audit 只作提示不改状态）
- 3 个「期间缺失」→ 品牌页两次加载都超时（站点个别品牌页很慢），重试仍失败
- 1 个「页面不可达」→ `12053` 已 404（募集结束下架），但它已投递，无影响

最终数据质量：48 个全部有期间与图片、47 个有数量、36 个有文案；
**期间字段混入非日期内容 0 个、数量字段混入文案 0 个**。
